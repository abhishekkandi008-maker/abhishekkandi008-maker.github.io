Google Antigravity CLI was built entirely using vibe coding — probably. Write prompts, drink iced coffee, pray to the AI. Just kidding. Mostly. As a developer I know security is a continuous process, not a one-time task, and it is always a major pain point. Because when the “developer” is an LLM with tools, nobody drew real boundaries. If you tell it to float your laptop, it will try. If an AI tells it to delete your hard drive, it says “I love that journey for you!” — and deletes everything.

This blog is the exploit that made the joke stop being a joke: the same attack chain I reported through Google’s AI VRP, reproduced end-to-end against Google Antigravity — prompt injection → case-blind bypass of a sensitive-file HITL check → silent settings write → extension-triggered RCE.

What “going rogue” means for Antigravity CLI

Antigravity is an agent-first surface: chat is not the product; doing things is. CLI / agent tooling that can create files, edit config, and drive the IDE inherits your privileges. “Going rogue” in this research was not a cartoon evil monologue. It was the agent quietly rewriting the one file that decides which binaries your editor will run — a write that was supposed to require your explicit approval.

Zero boundaries, in product form

Vibe coding ships capability first. Safety is a glob, a classifier, a require_confirmation flag. Miss one case fold on Windows and those boundaries evaporate. The model does not need to defeat the safety UI if the safety UI never schedules.

On Windows, settings.json and settings.JSON are the same file. Antigravity / Gemini’s sensitive-path gate treated them as different. Injected instructions steered a write at the wrong casing → auto-approve → real settings poisoned → next IDE action spawns attacker-chosen code.

0 — Delivery: poison the context

You do not jailbreak Antigravity into confessing crimes. You get it to read attacker-controlled instructions while it holds write tools.

  • Shared git repo with README / setup notes the agent is eager to “follow”
  • Ticket, paste, or chat that looks like onboarding help
  • Any social pattern where being helpful means creating editor config without a human reading every path

Prompt injection is delivery. The exploit is privilege past human controls.

1 — The CLI / agent already has your privileges

Developer opens the workspace in Antigravity (or Gemini-backed VS Code agent workflows that share the same failure mode). Ordinary source edits can auto-approve. Sensitive trees — .vscode, .env, .git — are supposed to hit HITL. That split is the disk-mutation security model.

2 — Steer config, not malware.exe

The injected instructions do not need to say “run calc.” They need the agent to create or edit workspace settings — the file that names validators, tasks, language-server paths, process images. Config is code with extra steps. 

{
  "php.validate.executablePath": "C:\\windows\\system32\\calc.exe"
}

Calculator is the demo. Real attacks point that sink at a loader, reverse shell, or quiet implant. Same family: tasks that run shells, MCP stdio commands, any setting that names a binary.

3 — The bypass: settings.JSON is not sensitive (to the checker)

Conceptual gate: 

const ALWAYS_CHECKED_EDIT_PATTERNS: Readonly<Record<string, boolean>> = {
  '**/.vscode/*.json': false,  // false → require manual approval
};

Match → Confirm. Miss → auto-approve. On case-sensitive filesystems this often works. On Windows it does not: the OS folds case; the glob does not.

The mismatch

Security control: case-sensitive string / glob match.
Operating system: case-insensitive path resolution.
Attacker: write .vscode/settings.JSON or .VSCODE/…; OS updates real settings.json; HITL never fires.

That is Antigravity CLI going rogue in the LinkedIn sense: it does not argue with you. It cheerfully completes a “setup” write the policy already misclassified as safe. I love that journey for you.

4 — Silent poison on disk

The write lands. Windows folds the name. Real workspace settings now contain attacker-chosen keys. No human clicked Confirm. The chat can look like a successful onboarding turn.

5 — Ordinary IDE behavior finishes the RCE

Open or save a PHP file (or whatever triggers the configured validator). The extension spawns executablePath. No separate “run this binary” tool approval. Config → process spawn → code execution as the user.

6 — Persistence after the agent leaves

Once settings are rewritten, the malicious session can end. The next ordinary IDE action — on this machine or another that synced the same poisoned config — finishes the job again. Blast radius: shared repos, team projects, agent-assisted onboarding — not unauthenticated remote entry.

Severity nuance

Local chain + user interaction (developer uses the agent / opens the workspace). Severity is the silent bypass of the control that was supposed to make that interaction safe.

Why vibe coding makes this worse

Antigravity CLI’s product bet is speed: an agent that ships work. Vibe-coded stacks optimize for “the model said yes and the tool ran.” Boundaries are afterthoughts — globs, allowlists, remembered approvals — until an attacker proves they are stringly typed.

What the agent thought

Helpful CLI turn

“Create settings so PHP validation works.” In-character. Looks like setup, not exploitation.

What the host did

Windows + IDE

Wrote real .vscode/settings.json, skipped HITL, left a process-spawn sink for the next editor action.

Security as a continuous process means: every new tool, every new path policy, every “approve once” memory is another place Antigravity can go rogue without sounding rogue. Offensive testing has to be part of every agent build — exactly what the LinkedIn comments called out.

Containment ≠ sensitive-path policy

Digging into Gemini CLI / core path checks made the pattern wider than one glob. “Is this path under the workspace root?” is not “may we silently mutate this capability file?” 

// Conceptual — containment alone is not policy
private isPathWithinRoot(pathToCheck: string, rootDirectory: string): boolean {
  const relative = path.relative(rootDirectory, pathToCheck);
  return (
    !relative.startsWith(`..${path.sep}`) &&
    relative !== '..' &&
    !path.isAbsolute(relative)
  );
}

On Windows, oddly cased .GIT / .vscode still look “inside.” Sensitive segments need case-insensitive normalization (plus trailing-dot / ADS awareness) before ASK / DENY — not equality on the string the model typed.

What the fix scar tissue looks like

After remediation, Gemini CLI-style safety normalizes segments before policy: 

const clean = trimTrailingSpacesAndDots(
  segment.split(':')[0],
).toLowerCase();

if (clean === '.git' || clean === '.env' || clean === 'node_modules') {
  hasBlockedSegment = true;
}
if (clean === '.vscode') {
  isVscodePath = true;  // → ASK_USER
}

Who gets hit

  • Clone / open a poisoned repo the Antigravity agent is asked to set up
  • Team projects where poisoned settings ride along in git
  • Agent-assisted onboarding (“follow my codebase / main.py”)
  • Antigravity-first workflows — more tool use, more trust that HITL will catch the scary writes

Persistence is the quiet part. The agent can leave. The next validate/save finishes RCE.

Takeaways

Antigravity CLI can go rogue without sounding evil — silent capability-file writes are enough.

Match policy to the OS, not to the string the LLM typed. Case, ADS, trailing dots.

HITL that never schedules is worse than no HITL — operators think they are protected.

Config is code. Treat silent settings.json mutation like silent .git/hooks writes.

Vibe coding does not ship boundaries. Security stays continuous: offensive tests on every agent build, system policy that still works when the model is “helpful.”

Prompt injection delivers; policy bugs exploit. Closing the case fold closed Antigravity / VS Code settings RCE and related sensitive-dir stories at one choke point.

If you ship an agent CLI

  • Normalize paths before every allow / deny / ask decision
  • Separate “inside workspace” from “sensitive path”
  • Always-ask (or deny) for .vscode, .git, env files, and any setting that can name a binary
  • Never treat “user is chatting” as “user approved this write”
  • Assume prompt injection; design so helpful setup still cannot skip HITL on capability files

Antigravity CLI can go rogue. The fix is not iced coffee and better prompts. It’s policy that matches the filesystem — and a process that keeps proving it.
