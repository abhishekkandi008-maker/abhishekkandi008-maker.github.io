Kernel Conquest: Root Access in Azure Cloud Shell via Netfilter UAF

04 Aug, 2026 | Nullcon Goa 2025 Kernel Azure Cloud Shell MSRC

Azure Cloud Shell looks like a friendly browser terminal: authenticated, pre-configured, managed by Microsoft. What it does not give you by default is root. At Nullcon Goa 2025, Alla Vamsi Krishna and I showed how kernel bugs in that environment turned “unprivileged Cloud Shell user” into a root shell — and what that does (and does not) mean for multi-tenant cloud isolation.

Full session recording: Nullcon Goa 2025 — Kernel Conquest on YouTube.

Disclosure

Both issues were reported to Microsoft (MSRC), fixed with an updated kernel and hardened Cloud Shell controls, and presented publicly after mitigation. This post summarizes the talk; it is not an exploit recipe.

Speakers & setting

Alla Vamsi Krishna (Indian Institute of Science, Bengaluru) and Kandi Abhishek Reddy (Nokia) co-presented at Nullcon Goa 2025 (talk date ~2 March 2025). The research sits at the intersection of cloud security, Linux kernel exploitation, and bug bounty / MSRC coordination.

The practical prompt was almost mundane: Cloud Shell would not let us install packages without root. Bring-your-own tooling, no local VM handy — so the question became: can we break into root inside this managed shell?

What Azure Cloud Shell actually is

Azure Cloud Shell is an interactive, browser-accessible, authenticated terminal for managing Azure resources. Sessions are short-lived (on the order of ~20 minutes of inactivity before cleanup), filesystem state you care about belongs on the mounted cloud drive, and the runtime is Microsoft’s Azure Linux–based container stack — not a full VM you own end-to-end.

Important distinctions from the talk:

  • Container ≠ VM. A container shares the host kernel; a VM owns its own. Escaping a container is about host privilege, not inventing a new machine.
  • No root by design (pre- and post-hardening). Cloud Shell runs unprivileged. sudo -l after the fix makes the “no new privileges” posture explicit.
  • Limited egress. The Cloud Shell container typically has no useful outbound network for the attacker’s comfort — exploitation has to work in that constrained environment.
  • Single-tenant hypervisor boundary. After disclosure, MSRC guidance emphasized isolated VMs per instance, non-reused VMs, and user data stored outside the container so a container escape does not become cross-tenant theft by default.
Boundary model

A container is not a hard security boundary. Hypervisor / single-tenant isolation is. Getting root (or escaping into the host of your Cloud Shell VM) escalates power inside your session; it does not automatically mean reading another tenant’s shell. Cross-tenant still needs something else — open surfaces, Hyper-V escapes, shared state — which is a different research problem.

Two bugs, one goal: elevate inside Cloud Shell

We reported two kernel-facing issues through MSRC:

1. Open vSwitch integer manipulation

Severity: Important · Impact: Elevation of Privilege

Integer / bounds manipulation in the Open vSwitch kernel module path that could be steered into out-of-bounds privilege escalation inside the Cloud Shell environment.

2. nftables / Netfilter Use-After-Free

Severity: Moderate · Impact: Unauthorized access / control

A dangling pointer inside a Netfilter / nftables transaction — improper reference counting across prepare / commit / release — yielding a classic UAF, with demo paths that leaked heap / helped KASLR bypass before a root shell.

Affected context called out in the talk abstract: Azure Cloud Shell on kernels in the 5.10.102.2-microsoft-standard line and related builds prior to the 6.9-era fixes Microsoft shipped for the platform.

Netfilter primer (why this code path matters)

Netfilter is the Linux packet-filtering framework behind firewalling, NAT, and classification. Hooks sit at well-defined points in the networking stack (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING). Userspace configures tables, chains, and rules; the kernel implements them.

nftables talks to the kernel over netlink-style IPC. From userspace you batch operations — new table, new chain, new rule, delete rule — into a transaction. That transaction has phases. Get reference counting wrong across those phases and you get use-after-free, not a polite error.

Root cause: improper reference counting in the transaction

The vulnerable story is about a set S and a chain C in the network stack: if an element expires or is unbound before the reference count is updated correctly, you get invalid memory access — a Use-After-Free during abort / error paths.

Prepare

The kernel walks the batch, allocates structures, validates inputs, and stages new objects (tables, chains, sets). Objects move onto a pending / commit list. Activation flags and object state matter here: you are building a world that does not fully exist yet.

Commit

Walk the commit list. Create / update / delete under RCU (Read-Copy-Update). Activate new entries; deactivate old ones. Error handling must keep reference counts coherent. The dangerous code paths sit in Netfilter’s API layer (talking around nf_tables transaction helpers that deactivate / unbind sets): if prepare fails partway, deactivation can decrement refs without leaving objects in a safe state.

Release

Destroy the transaction, free resources, walk the commit list again, drop references. If counts go wrong — including paths that effectively allow invalid / negative-style states without proper validation — memory can be freed while something still holds a dangling pointer.

The mismatch

Transaction abort / prepare-error paths must undo binds as carefully as the happy path creates them.
Miss a deactivate / unbind on an anonymous set (or similar), free the object, keep a pointer → UAF.
From there: heap spray / reclaim, info leak, KASLR defeat, escalate.

Conceptually, the failing pattern is: flag-driven cleanup that does not run (or runs incompletely) when nft_trans_prepare-style paths error out, leaving bindings and refcounts inconsistent with what the destroy path assumes.

In the recorded demo (pre-fix Cloud Shell): start as a normal user (id), run the PoC against the then-current Microsoft standard kernel (~5.10.102 line), land a root shell. Separately, the nftables UAF path showed heap address leakage useful for defeating KASLR before the same end state: root.

Success rate on the kernels we cared about was imperfect but real (roughly “7/10” in Q&A) — version-sensitive, like most kernel UAFs.

Impact: scary for the session, constrained for the fleet

Successful exploitation meant:

  • Elevated privileges inside the user’s own Cloud Shell environment
  • Potential container escape within that user’s session
  • Broader access to cloud resources already reachable under that user’s identity / session

What it did not automatically mean (by Microsoft’s post-fix architecture story):

  • Cross-tenant compromise via a shared kernel on a shared VM — Cloud Shell moved to / emphasized non-shared, isolated hypervisor VMs
  • Automatic access to other users’ session data stored outside the container

Cloud Shell is a single-user execution environment. Elevate to root and you still only own your session’s resources — by design, after the hardening pass. Whether every adjacent control (capabilities, open ports, Hyper-V) is forever airtight is a separate, ongoing research question; we called that out as future work, not as a finished cross-tenant exploit.

What Microsoft changed

After CVD with MSRC:

  • Updated kernel on Cloud Shell (demo time: latest builds; we noted a mid-January-era refresh in the talk)
  • Privilege posture: no new privileges / no casual sudo path to root for the interactive user
  • Isolation messaging: container escapes restricted so one user session does not compromise another; VMs not reused in a way that would expose leftover user data
  • Capability / hardening flags on the container profile (some of which remain interesting research surfaces)

By the time we wanted a live demo on stage, the public Cloud Shell we hit was already patched — a recorded PoC from the vulnerable window carried the proof.

Takeaways

Managed shells still run real kernels. “Browser terminal” marketing does not remove nftables, Open vSwitch, or RCU. If userspace can drive those APIs, kernel bug classes follow.

Isolation layers are layered lies until proven otherwise. Namespaces, capabilities, “no root,” even Hyper-V — each is a boundary with a different failure mode. Containers are especially easy to over-trust.

Reference counting on abort paths is where adults lose. Happy-path activate/deactivate is tested. Prepare-error + anonymous-set cleanup is where dangling pointers hide.

Impact statements matter as much as CVSS. Root in your own Cloud Shell is serious for that user and for anything the session can already touch. It is not the same claim as “broke Azure multi-tenancy.” Say the first clearly; don’t inflate into the second without a second exploit.

Security is a team sport. CVD with MSRC, public talk after fix, and honest Q&A about what still needs research beat silent hoarding or overclaiming.
