Arbitrary File Write to RCE in Antigravity Browser via SaveScreenRecording

05 Aug, 2026 | Google VRP $10,000 RCE Antigravity Browser Chrome Extension

Antigravity’s agent-first IDE ships a browser. That browser ships a Chrome extension. The extension shipped externally_connectable: <all_urls> and a SaveScreenRecording action that took a attacker-chosen filename and raw bytes, then asked the language server to write a file. Path traversal turned “save this WebM” into “write wherever you want on the user’s profile” — and from there into classic Windows persistence / code execution.

This post walks the Google VRP report filed by Sudhanshu Rajbhar against the Antigravity browser extension: triaged, accepted, fixed, and rewarded $10,000. It sits next to the agent-side Antigravity chains on this site — When the Agent Went Rogue and Antigravity CLI Can Go Rogue — as the complementary lesson: when the product opens a browser for the agent, the extension trust boundary is part of the host compromise story.

The chain in one line: attacker page in Antigravity browser → chrome.runtime.sendMessage → SaveScreenRecording with path traversal → language-server arbitrary write → startup / persistence RCE.

Credit & disclosure

Original report: Sudhanshu Rajbhar · Google VRP · Antigravity. Timeline from the report: reported / triaged (21 Nov 2025) → accepted (27 Nov 2025) → fixed (21 Dec 2025) → reward decided $10,000. This writeup elaborates the already-fixed trust-boundary failure for the Antigravity series — not a live exploit against current builds.

Why the Antigravity browser extension mattered

When you ask Antigravity to “open example.com,” it does not hand you a random Chromium profile with no privileges. It launches the Antigravity browser with an extension that bridges the page world to the local language server — screen recording, tab IDs, RPC proxies, the works.

That bridge is powerful on purpose. It is also a confused-deputy surface: anything that can talk to the extension inherits a slice of host capability. Chrome’s answer to “who may talk to my extension from a webpage?” is externally_connectable.

The config that caught the reporter’s eye

externally_connectable.matches was set to <all_urls>. Any origin loaded in the Antigravity browser could call chrome.runtime.connect() / chrome.runtime.sendMessage() against the extension ID. The trust model for “who may drive SaveScreenRecording” was effectively: whoever rendered a page. 

"externally_connectable": {
  "matches": [ "<all_urls>" ]
}

Once every site is a peer of the extension, the only remaining question is whether any message handler does something unsafe with attacker-controlled fields. One of them did.

0 — Delivery: any page the agent (or user) opens

No extension store phishing. No native installer. The victim — or the agent acting on their behalf — opens an attacker-controlled URL inside the Antigravity browser. That is a normal product action: “browse this docs site,” “open the staging URL,” “check this repro page.”

1 — External messaging is wide open

With <all_urls>, the page’s DevTools console (and any script on the page) can reach the extension. Handlers observed on the wire included things like:

  • SaveScreenRecording
  • getCurrentTabId / registerTargetID
  • startScreenRecording / stopScreenRecording
  • proxyRpcCall / rpcCall

Screen recording is a feature. Exposing its save path to every website is a privilege boundary.

2 — SaveScreenRecording takes content and a path

The interesting handler checked for an object shaped like: action SaveScreenRecording, a byte array field, a string filename, and another string path component (obfuscated field L in the minified build). Conceptual gate from the report: 

if (!a || typeof a !== "object"
    || a.action !== "SaveScreenRecording"
    || typeof a.za !== "object"
    || typeof a.filename !== "string"
    || typeof a.L !== "string") {
  // reject
}

Types were checked. Path safety was not. The bytes in za became file content. filename and L were concatenated into the destination path under the Antigravity recordings / brain directory.

3 — Extension → language server RPC

The extension did not write the file itself in the page process. It packaged a protobuf-ish request and called the local language server: 

/exa.language_server_pb.LanguageServerService/SaveScreenRecording

That is the same class of host-side service the IDE trusts for agent work. Error messages from failed opens leaked the resolved path — enough to confirm traversal was landing where the reporter aimed: 

Failed to save video file: open
C:\Users\STARK-PC\.gemini\antigravity\brain\aaa\screen-recordingss-….webm:
The system cannot find the path specified.
The mismatch

Feature intent: save a recording under a managed Antigravity directory.
Security control: type-check the message fields.
Missing control: canonicalize / jail the path; authenticate the caller beyond “any webpage.”
Attacker: ../ sequences in filename / L until the write escapes into C:\Users\<user>\….

4–6 — Traversal → arbitrary write

Concatenating untrusted path segments is the oldest write bug in the book. From the intended brain / recordings tree, enough ../ reaches the user profile. Content is fully attacker-controlled (the “video” bytes never had to be a real WebM).

7 — From write to RCE

Arbitrary write under the user profile is already game over for many threat models. The report’s impact story on Windows is the obvious persistence path: drop a payload where the OS will execute it on logon (e.g. the user Startup folder), then wait for the next reboot / sign-in. No second vulnerability required — only a file write the product already performed on the attacker’s behalf.

Proof of concept (file write)

Reproduction shape from the report (Windows; Antigravity browser with the extension initialized). Extension ID as observed in the report: eeijfnjmjelapkebgockoeaadonbchdd. 

<script>
const content = "shirley: hey sudi, I love you ;)";
const bytes = new TextEncoder().encode(content);
const EXTENSION_ID = "eeijfnjmjelapkebgockoeaadonbchdd";

function sendRecording() {
  chrome.runtime.sendMessage(
    EXTENSION_ID,
    {
      action: "SaveScreenRecording",
      filename: "../poc.txt",
      za: Array.from(bytes),
      L: "../../../test",
      video_data: "aaaaaaaaaaaaaaaaa"
    },
    (response) => console.log("Response from Extension:", response)
  );
}

sendRecording();
</script>

Steps, condensed:

  1. Open Antigravity IDE; prompt it to open a URL so the Antigravity browser launches.
  2. Confirm chrome.runtime is available in DevTools on a loaded page (refresh if needed).
  3. Open the PoC HTML in that browser.
  4. Observe a new file under the user profile (report example: C:\Users\STARK-PC\poc.txt with the chosen content).
Scope note

This is not “drive-by on every Chrome user.” It requires the Antigravity browser / extension path — typically after the IDE has been used to open web content. Inside that product surface, origin isolation for extension messaging was effectively absent, so a single malicious page was enough for the write primitive.

Attack scenario

Realistic story:

  • Developer uses Antigravity; agent opens docs, staging, or a “repro” link the attacker controls.
  • Page JS messages the extension; path traversal writes outside the recordings jail.
  • Attacker places a persistence binary or script where Windows will run it later — or overwrites other high-value files the user / tooling will execute.
  • Compromise survives the browsing tab. The agent can leave; the file remains.

Same family of failure as the agent HITL bypasses on this blog: a helpful product capability (record screen / write settings / run shell) without a boundary that matches how the OS actually resolves trust.

Root cause

Three failures stacked:

  1. Over-broad externally_connectable. <all_urls> made every site a privileged peer of the extension. Feature RPC should have been limited to known Antigravity origins — or better, not exposed to web pages at all.
  2. Untrusted path concatenation. filename and related segments were not confined to a basename / allowlisted directory after realpath-style resolution.
  3. Content-controlled write into a host service. The language server honored the path and bytes from a message that any page could forge.
Agent products multiply deputies

Antigravity already has an agent that can write files. The browser extension was a second deputy with a different entrypoint and weaker caller checks. Defenders who only audit the chat tool policy miss the extension ↔ language-server pipe.

What a correct fix looks like

  • Narrow externally_connectable to specific Antigravity / first-party origins — or remove external messaging for save APIs entirely.
  • Never take relative paths from the page. Accept only a recording ID; the host chooses the absolute path under a fixed jail.
  • Canonicalize and enforce a directory prefix on the language-server side even if the extension is compromised or confused.
  • Authenticate / authorize sensitive RPCs with a secret or native messaging channel that web content cannot forge.
  • Treat screen-recording save as a privileged operation — same severity class as “write arbitrary bytes to disk,” because that is what it was.

Google accepted and fixed the issue; the report marks reward decided at $10,000. Anyone still on builds from before the Dec 2025 fix window should update.

How this fits the Antigravity series

On this site the Antigravity / Gemini agent stories were about policy that does not match the filesystem (case-blind HITL on settings.json) and shell policy that does not see eval. This browser bug is the cousin: extension policy that does not match who can call you, plus path policy that does not jail writes.

Three deputies, one host:

  • Agent tool loop → disk / settings
  • CLI shell tool → OS commands
  • Browser extension → language-server file write

Secure the chat box and leave <all_urls> on a save-to-disk RPC, and the host is still for sale.

Takeaways

externally_connectable: <all_urls> is a loaded gun next to any handler that touches the filesystem or a local privileged service.

Type checks are not path checks. typeof filename === "string" does not mean the string is safe to open.

Arbitrary write is RCE with patience on desktop OSes — Startup folders, shell extensions, editor config, and helper binaries all turn bytes into execution.

Agent IDEs need a full trust map of every bridge: extension, language server, CLI, MCP — not only the model’s tool allowlist.

Credit again to Sudhanshu Rajbhar for the Google VRP report that made this chain explicit. On to the next boundary.
