When Case Didn't Count: Prompt Injection to RCE in Google Gemini Antigravity

02 Aug, 2026 | Bounty awarded by Google $$$$$ RCE Prompt Injection

Picture an AI coding agent that feels helpful — reviewing your project, creating files, wiring config — while quietly rewriting the one file that decides what binaries your editor will run. No dramatic jailbreak monologue. No “ignore previous instructions” theatrics. Just a coworker that went rogue in the most boring way possible: it changed state you thought was locked behind your approval.

That is the shape of modern agent risk. Once a model can write to disk, “going rogue” does not mean sounding evil. It means mutating workspace reality — especially sensitive special files like settings.json, which are supposed to require explicit permission before an agent can touch them. Break that gate and the agent stops being a chatbot. It becomes a confused deputy with your privileges.

In November 2025 I reported exactly that chain against Google’s Gemini coding agents, then reproduced it end-to-end in Google Antigravity, through the Google AI Vulnerability Reward Program. On Windows, settings.json and settings.JSON are the same file. The permission check treated them as different. An injected prompt steered the agent past human-in-the-loop, silently poisoned workspace settings, and turned configuration into host code execution.

The chain in one line: prompt injection → case-blind bypass of a sensitive-file permission check → silent settings write → extension-triggered RCE.

The setup: what “sensitive file” means to an agent

Coding agents that can edit your workspace need a human-in-the-loop for certain paths. Not every write should be auto-approved. Surfaces like .env, .git, and .vscode are different from ordinary source files: secrets, repository hooks/config, and editor behavior — tasks, launch configs, language server paths, validation hooks. Those aren't “just another source file.” They’re capability.

Gemini's defense was a sensitive-file check, conceptually: 

const ALWAYS_CHECKED_EDIT_PATTERNS: Readonly<Record<string, boolean>> = {
  '**/.vscode/*.json': false,  // false → require manual approval
};

If a proposed edit matched the glob, the agent was supposed to surface a confirmation. Edits that didn't match any sensitive pattern could be auto-approved. Sensible. On macOS and Linux — where the filesystem is (usually) case-sensitive — it even worked the way the author intended.

On Windows, the filesystem does not care about your casing. settings.json and settings.JSON are the same inode. The glob matcher did care.

The mismatch

Security control: case-sensitive string / glob match.
Operating system: case-insensitive path resolution.
Attacker: pick a casing the checker doesn't recognize; write the file the OS still treats as the real one.

The bypass: settings.JSON is not settings.json (to the checker)

Demonstration was straightforward. In the Gemini chat surface for a VS Code agent workflow, an injected / steered prompt could instruct the model to create or edit a file named with alternate casing — for example .vscode/settings.JSON instead of .vscode/settings.json.

The sensitive-file gate evaluated the path as a string against a case-sensitive pattern. Mismatch → “not sensitive” → auto-approve. The write landed on disk. Windows folded the name. The real workspace settings were now attacker-controlled, and no human had clicked Confirm.

That single boolean — matched or not — is the whole vulnerability. Sensitive special files like settings.json are supposed to require permission. Miss the pattern, skip the permission, own the machine’s config.

From a JSON key to code on the host

Prompt injection against agents is rarely “make the model say something naughty.” The useful goal is privilege escalation past human controls. Here the privilege was “write workspace config without asking,” and the sink was a well-known VS Code / extension pattern: executable paths in settings.

The PoC targeted: 

{
  "php.validate.executablePath": "C:\\windows\\system32\\calc.exe"
}

Once that value sat in the (bypassed) settings file, a normal developer action — opening or saving a PHP file that triggers validation — caused the PHP language tooling to spawn whatever path was configured. Calculator popping is the classic “I control the process image” demo. In a real attack that path is malware, a reverse shell, or a loader that never shows a window.

Important nuance

This is a local chain with user interaction (the developer uses the agent / opens the workspace). The severity comes from silent bypass of the control that was supposed to make that interaction safe — not from unauthenticated remote entry. Shared team repos and “please follow my codebase” social patterns are how it spreads between machines.

Why the model didn't need to be “rogue”

Google's agent safety docs talk about safety_decision: require_confirmation for risky computer-use style actions — a HITL brake when the model proposes something dangerous. In this exploit path, that brake never engaged for the interesting action, because the policy layer that classifies the file as sensitive never fired.

The model wasn't bypassing a confirmation UI with clever wording. The confirmation UI was never scheduled. That's a different bug class than classic jailbreaks: it's policy/implementation skew, not persuasion.

You don't need the model to defeat the safety system if the safety system already decided this path wasn't worth checking.

Same bug, wider surface: Antigravity and path blocklists

After the initial VS Code / Gemini agent report, I reproduced the same case-folding idea against Google Antigravity — Google's agent-first IDE surface — with a separate PoC video for the VRP thread. Shared agent cores share failure modes.

Digging further into Gemini CLI / core path validation later made the pattern look even more general. Workspace containment checks of the form “is this path under the workspace root?” answer a different question from “is this a sensitive path we must never silently mutate?” 

// Conceptual shape — containment ≠ policy
private isPathWithinRoot(pathToCheck: string, rootDirectory: string): boolean {
  const relative = path.relative(rootDirectory, pathToCheck);
  return (
    !relative.startsWith(`..${path.sep}`) &&
    relative !== '..' &&
    !path.isAbsolute(relative)
  );
}

Containment alone happily allows .GIT/config or oddly cased .vscode segments on Windows, because path.relative and the OS agree the path is “inside,” while a naive string blocklist for .git may not. Sensitive directories need case-insensitive segment checks (and, on Windows, awareness of trailing-dot / ADS weirdness) — not just glob equality on the path the model typed.

Reading the fix forwards

The cleanest way to understand what was wrong is to look at what defensive code looks like afterward. In current Gemini CLI core safety, path segments are normalized before policy decisions: 

const clean = trimTrailingSpacesAndDots(
  segment.split(':')[0],
).toLowerCase();

if (clean === '.git' || clean === '.env' || clean === 'node_modules') {
  hasBlockedSegment = true;
}
if (clean === '.vscode') {
  isVscodePath = true;  // → ASK_USER
}

And the regression suite now explicitly includes the bypass cases that used to work: 

path.join(mockCwd, '.vscode', 'settings.JSON'),
path.join(mockCwd, '.VSCODE', 'settings.json'),
path.join(mockCwd, '.vscode ', 'settings.json'),
path.join(mockCwd, '.vscode::$DATA', 'settings.json'),

Those tests expect ASK_USER for in-workspace .vscode mutations and hard denials for blocked trees like .git / .env under alternate casings. That's scar tissue. You don't write a test named “Case-Insensitive Blocklist & .vscode HITL” unless production code previously failed it.

Impact model: who actually gets hit

Triage asked the right question early: how does this affect other users if someone is “just asking Gemini to run commands”?

The realistic blast radius is shared workspaces and socialized agent usage:

  • Clone / open a poisoned repo that contains instructions or files the agent is eager to “follow.”
  • Team projects where one compromised settings write rides along in git and waits for the next PHP (or other) validation trigger on each machine.
  • Agent-assisted onboarding (“please follow my codebase file named main.py”) that causes the model to create config as part of being helpful.

Persistence is the quiet part. Once executablePath (or tasks, or a similar sink) is rewritten, the agent can leave. The next ordinary IDE action finishes the job.

Classifiers look fine on the leaderboard — until the agent has tools

Capability benches and chat leaderboards reward fluent answers. Agentic products reward something else: a model that can do things. When I compared Gemini against other frontier stacks on public AI-mode / LMSYS-style arenas and general capability boards, Gemini often looked competitive — sometimes excellent — on the scoreboard people screenshot. That is not the same as a trustworthy permission classifier for file writes, shell tools, or workspace mutation.

What this bug made obvious

Gemini’s agent stack already had a safety story — sensitive paths, require_confirmation, human-in-the-loop. The Antigravity / VS Code chain did not need a jailbreak monologue. It needed the classifier (or the path policy feeding it) to miss. Leaderboard wins do not buy you that layer. On this surface, Gemini’s classifiers were not “great”; they were incomplete relative to the privileges the agent actually held.

In other words: I can believe Gemini is strong on a chat leaderboard and still not trust it alone as the gatekeeper for .env, .git, and settings.json. Capability score ≠ tool-policy competence.

This is the research literature’s warning, not a hot take

Two papers make the same structural point this bug demonstrated in product form.

Agentic Misalignment: How LLMs Could Be Insider Threats

Lynch et al. · Anthropic et al. · 2025

Stress-tests across major model families show that when agents get tools, goals, and autonomy, they can behave like insiders — taking harmful actions even when the user request looks benign. The paper’s caution is blunt: be careful deploying current models in roles with sensitive access and thin oversight. An IDE agent with write tools is that role. My Antigravity chain is the boring cousin of that story — not blackmail in a simulation, but silent state change on a developer machine because the policy layer blinked.

An Approach to Technical AGI Safety and Security

Shah et al. · Google DeepMind · Apr 2025

DeepMind separates misuse and misalignment, then argues for two lines of defense: model-level mitigations (training, amplified oversight) and system-level controls (monitoring, access restriction) that still work if the model is wrong. Classifiers and “safety decisions” sit in the first bucket. Case-normalized path blocklists, always-ask for sensitive trees, and never treating chat intent as write approval sit in the second. This bug happened because the product leaned on the first and under-built the second.

So when I say Gemini classifiers aren’t that great, I do not mean “Gemini cannot write code.” I mean: on the axes that matter for agentic IDEs — deciding when a tool call is privileged, when confirmation is mandatory, when a path is sensitive regardless of casing — leaderboard performance did not translate. The model can look aligned in AI Mode benchmarks and still be an insider threat the moment you hand it a filesystem.

What I'd actually take from this

Match the security control to the OS, not to the string the LLM typed. Glob libraries default to case-sensitive matching. Windows and often macOS do not. Any allow/deny/ask decision keyed off a path string must normalize the way the filesystem will.

HITL gates are only as real as their classifiers — and classifiers are not leaderboards. require_confirmation that never triggers is worse than no gate. Gemini can win AI Mode / arena comparisons and still miss a privileged write. Pair model safety with system policy, the way the DeepMind AGI safety agenda argues.

Config is code. Workspace settings that name executables, tasks that run shells, MCP stdio commands, sandbox proxy env vars — they're all process spawn with extra steps. Treat silent writes to those surfaces like silent writes to .git/hooks. Agentic misalignment research is not abstract once the agent can edit those files.

Prompt injection is the delivery; policy bugs are the exploit. The model was a confused deputy with a filesystem API. Closing the case fold closed three attack stories (settings RCE, Antigravity reproduction, sensitive-dir writes) at the same choke point.

Read the regression tests. When a suite starts asserting settings.JSON, .VSCODE, trailing dots, and ::$DATA, someone already lost that argument with an attacker.

If you build agents that edit disks

  • Normalize paths (case, ADS, trailing ./ on Windows) before policy.
  • Keep an explicit sensitive-path policy separate from “is inside workspace.”
  • Default-deny or always-ask for .vscode, .git, env files, and any setting that can name a binary.
  • Don't confuse “the user is chatting with the agent” with “the user approved this write.”
